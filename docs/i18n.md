# Internationalization

## Locales

Five locales in `messages/`: `en-US` (default), `zh-CN`, `de-DE`, `fr-FR`, `es-ES`. Routing is defined once in `src/i18n/routing.ts` with `localePrefix: as-needed`: default-locale URLs carry no prefix, other locales are prefixed only when needed.

## Resolution order

1. `NEXT_LOCALE` cookie (set for 1 year, `SameSite=Lax`) when it names a supported locale.
2. `Accept-Language` header with exact match, else base-tag fallback (`en` to `en-US`, `zh` to `zh-CN`, `de` to `de-DE`, `fr` to `fr-FR`, `es` to `es-ES`).
3. `en-US` default (also the `defaults.locale` in `deployment.yaml`).

Middleware writes the resolved locale to the `x-locale` request header and refreshes the cookie. Portal timezone comes from `defaults.timezone` in `deployment.yaml` (`Asia/Shanghai` shipped); user display prefs (widgets, theme, density) persist via `/api/me/prefs` and are unrelated to locale.

## Adding keys

1. Add the key to all five `messages/*.json` files in the same edit. No locale ships a partial file.
2. Use ICU plurals where counts appear; `zh-CN` uses `other` only (no plural categories).
3. Keep placeholder names identical across all five files (`{count}`, `{name}`), and keep markup out of message strings.
4. Run `pnpm verify` before commit: oxfmt normalizes JSON formatting and typecheck catches missing-key usage.

## Expectations

Every user-facing UI string goes through `t()`. ESLint context plus code review enforce it; hardcoded English in JSX is a review rejection. oxfmt (4-space, double quotes, width 100) formats the locale files, so key diffs stay clean.

## Review status

English is authoritative. `de-DE`, `fr-FR`, `es-ES`, and `zh-CN` are machine-translated and need native-speaker review before any customer-facing release. Flag awkward keys in review rather than editing other locales silently; keep all five files in lockstep regardless.
